# 独立智能体审查（断后校验）协议

本协议是向具体用户交付解读结论前的 release gate。它审查候选答案是否被数据、规则与不确定性边界支持；它不证明占星结论的外部真伪，也不能由起草代理自我签字。

## 1. 触发与豁免

满足任一条件必须执行：

- 命盘、事业、婚姻、迁移、关系、时间窗口或既往事件的个人化解读
- 使用 SAV、BAV、Shadbala、度数、Nakshatra、dasha 日期等精确内容
- 完整报告、验证闸门结论、概率排序、行动建议或高风险领域的提醒
- 同一回复中同时含机械计算结果和解释性结论

以下情况可豁免：纯计算器输出、文件提取、schema 校验、无解释性结论的结构化 JSON、只向用户索要补充资料。混合输出一律视为需要审查。

## 2. 不可替代的独立性

- 起草代理**绝不能**审查、批准、豁免或解释自己的候选答案。
- 审查代理必须是全新启动的子代理，不继承起草代理的对话或工作上下文；支持该能力的宿主使用与 `fork_context=false` 等价的方式。
- 现有作者侧检查仅用于准备，不能替代本协议。
- **断后校验的唯一合法执行器**是新启动、干净上下文的审查子代理。主代理读取自己的草稿、作者侧 checklist、同一对话内的附带意见或普通“复核”都不构成审查。
- 审查超时、无法启动新子代理、上下文隔离失败、审查包不完整、返回格式不合法、`REVISE` 或没有明确 `release_allowed: true` 时，必须 fail closed：不得发送任何触发本协议的解释性结论、时间窗口、报告或数值判断；只允许输出本协议明确豁免的纯机械结果。
- 修订触及结论、数值、时间窗口、证据或置信度时，必须由**另一名新启动的干净上下文审查代理**复审。旧审查通过不能继承到新草稿。

## 3. 两阶段干净上下文流程

### Phase A：独立证据账本

在审查代理刚启动时，只传递：

1. `review_contract`：本协议版本、严重等级、通过门槛。
2. `user_request`：当前用户问题、交付范围和明确约束。
3. `authoritative_facts`：可供作者使用的结构化盘面/计算数据、来源与校验状态。
4. `applicable_rules`：本问题实际适用的 SKILL 约束和 reference 规则。
5. `allowed_context`：此分析模式明确允许使用的背景事实及其来源。
6. `output_requirements`：语言、格式、禁区和不确定性标准。

审查代理先形成独立的“证据 -> 可支持主张”账本，并记录哪些结论不能由现有资料支持。此阶段**不得看到候选答案**。

### Phase B：候选答案对照

只有 Phase A 完成并封存后，才传递：

- `candidate_answer`：准备发给用户的完整文本。
- `candidate_metadata`：skill/协议版本、数据来源标识、草稿版本号。

审查代理将候选答案与 Phase A 账本对照，输出固定 JSON verdict。

### 必须隔离的内容

两个阶段都不得传递：

- 起草代理的隐藏推理、工具轨迹、内部路由、自我检查、置信度笔记或“希望通过”的提示。
- 中间草稿、以前版本、过往审查结论、起草代理或模型身份。
- 当前分析模式不允许读取的用户传记、反馈或其他无关旧对话。
- Phase A 中的候选答案。提前展示会把独立审查退化为锚定式校对。

## 4. 审查检查项

审查代理必须检查：

- **证据可追溯性**：每项主要结论至少有两类独立盘面证据；精确数据仅来自已验证事实包。
- **数据状态一致性**：SKIP、失败、OCR 不明、出生时间不稳或来源冲突，不能写成确定结论。
- **推断边界**：结构层、窗口层和专名层不越级；不把背景事实或概率伪装成星盘直接事实。
- **时间和数值**：SAV/BAV、dasha、度数、Nakshatra 的来源与校验状态一致；未通过的 SAV/BAV 不得进入数值论断。
- **风险与范围**：高风险领域保留专业建议边界；回答覆盖请求范围、现实判断、盘面抓手和使用提醒。
- **语义一致性**：结论、证据、置信度、表格与免责声明没有互相矛盾。

## 5. 机器可读 verdict

```json
{
  "protocol_version": "independent-review-v1",
  "candidate_id": "string",
  "reviewer_context_id": "fresh-isolated-run-id",
  "phase_a_completed_before_candidate_access": true,
  "verdict": "PASS | REVISE",
  "release_allowed": false,
  "summary": "short factual statement",
  "findings": [
    {
      "id": "IR-001",
      "severity": "S0 | S1 | S2 | S3 | S4",
      "category": "unsupported_claim | contradiction | missing_required_qualification | policy_violation | data_provenance | scope | formatting | other",
      "candidate_location": "heading, claim ID, or short excerpt",
      "evidence_basis": ["fact-or-rule identifier"],
      "issue": "what is wrong",
      "required_remediation": "specific revision or deletion",
      "recheck_required": true
    }
  ],
  "required_remediation": ["flat list of release-blocking actions"],
  "reviewed_at": "ISO-8601 timestamp"
}
```

严重等级：

- `S0`：审查不可执行或不独立，例如上下文泄漏、Phase B 早于 Phase A、包缺失、超时或 verdict 损坏。必须换新审查代理重启。
- `S1`：虚构、不安全、明显矛盾或实质无证据的结论。删除或完全重写。
- `S2`：重大夸张、遗漏不确定性、强制规则误用、无支撑的时间或因果具体化。重写并补足边界。
- `S3`：漏答显式主题、缺必要证据轨迹或造成误导的重点安排。修正后方可交付。
- `S4`：非实质性的术语、清晰度或格式问题。可与 `PASS` 共存，但必须明确为非阻断。

`PASS` 仅在 Phase A 已完成、`release_allowed: true`，且没有未解决的 `S0-S3` 问题时有效。任何 `REVISE` 必须给出具体、可执行的修改项，不能只写“提高准确性”。

## 6. 交付与复审

起草代理收到 `PASS` 后才可交付候选答案。收到 `REVISE` 后必须落实所有阻断修改；只要修改影响结论、数值、时间、证据或置信度，就按第 3 节重新运行 Phase A 和 Phase B，并使用另一名新审查代理。

最终可向用户简要说明“独立审查已执行，结论为通过/修订后通过”。不得泄漏内部推理、路由、审查代理身份或不相关上下文。宿主没有能力启动新且干净上下文的子代理时，该能力不具备断后校验资格：不得交付触发本协议的解释性结论，也不能用作者自检、同一上下文代理或“未审查”标记绕过此门。
